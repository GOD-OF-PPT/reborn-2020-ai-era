建议首季工作2点＋手工小单1点＋研究/案例准备1点，共4点。研究不另附一份免费业务产出。玩家可拒绝或重排未执行计划；取消不退已发生成本。

## 4. 状态、命令与提交接口

沿内容15的GameRun、BusinessInstance、ProductionJob、Contract、CashReservation、MarketOrder、EquityAgreement、EventInstance、CommandReceipt实体建模。所有关系用稳定ID解析；业务操作不能直接赋值余额。定义ID、实例ID和回执ID分开。一次旧合同、班期、订单、账单或转化不能换页面后再领取收入。

GameRun最小状态包含runId、版本组、revision、ISO日期/检查点、背景、账户/流水/占款、行动/产能、业务/合同/任务、世界/记忆/证据、订单/权益、随机分域和因果记录。UI的保存状态与未提交候选由应用层管理，不把“已保存”当成可任意修改的规则收益字段。

命令封套固定commandId、runId、expectedRevision、actorId、kind、payload；kind/payload由有类型命令注册表逐项验证，未知命令、额外非法字段、越权主体与不存在引用明确拒绝。规范载荷哈希包含actorId/kind/payload及runId，不以expectedRevision改变同一业务意图的幂等身份；金额只能为安全范围内整数，哈希规范化不能依赖对象字段插入顺序。

| 调用边界 | 返回及责任 |
|---|---|
| 纯规则evaluate(state, command, content) | Rejected(reasonCodes)或Proposed(nextState, ledgerEntries, scheduledEvents, causeEntries, receipt)；不写浏览器、不读现实今天、不调用网络 |
| 只读preview(state, intent, content) | 用同一前提/成本函数产生已知成本、禁用原因和承诺；不消费随机、不生成隐藏真相、不预提交状态 |
| 应用submit(command) | 校验runId/格式/版本，查询已提交回执，再检查revision，在副本计算并校验不变量；通过持久化提交后发布新投影 |
| 持久化commitProposal(proposal) | 同一事务检查实际revision，并写快照/回执/日志；仅transaction complete为成功；abort保留旧提交 |
| 只读投影 | 仅展示当前主体的可见事实，个人/企业不合并，返回未履约/保护缺口/最早现金缺口，不触发结算 |

相同runId/commandId且规范载荷相同返回已提交回执，旧expectedRevision不导致重复扣费；相同ID不同载荷为COMMAND_ID_REUSED；不存在runId或非法载荷不能读取另一局回执。新命令旧revision为STALE_REVISION。拒绝和存储失败都不能部分应用账目；未保存候选可重试同一意图，但不得继续叠加新变更或假报回款成功。

同日顺序固定为世界更新→确定到账→到期义务→玩家动作→撮合→快照；同类按priority、instanceId稳定排序。推进停在需响应的检查点，未响应按明确默认分支记录。UI动画和展开次数不决定顺序。

四随机域world/market/opportunity/crisis；算法和派生方式在T04锁定并有固定向量回归，实例隐藏事实创建时保存。随机算法未实现前不能用Math.random临时替代。订单记录提交点与最早成交点，刚看到的信息只影响后续撮合。
