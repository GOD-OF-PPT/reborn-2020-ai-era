## Determinate findings — both reported to Root before this report

### P2 R1 — cancelled original action is described as executed/spent

src/ui/relay-records.ts:147, summaryFor's generic job path distinguishes draft, reserved and else. A true original action.status=cancelled falls into else and prints “已实际执行，已耗投入保留”. The original core cancellation path only cancels draft/reserved action; this is a pre-execution cancellation, not a spent action. The full jobLines statement correctly calls it cancelled, but RelayRecordBook.tsx:104 prints summary directly before the closed full-evidence details (line106), so the player sees the false claim by default. It is not repaired by having correct details below.

Required minimum: give cancelled its own original-state wording, preserve the original cost/AP as an original agreement, distinguish released reservation from actual spent cost/AP; keep executed/completed/interrupted factual and check executedAt consistently. Do not remove original amounts or invert failed saves into cancelled business results. The current two new tests contain no case of cancelled original action summary, so this semantic defect is not fenced by them yet.

### P2 R2 — supplier original movement chain omits later original payable cash payments

src/ui/relay-records.ts:284-295 constructs supplier movements only when the operation has a pool prepaymentId or sourceEventId equals supplierId. The actual core PayObligation writer at src/core/operations.ts:152 uses sourceEventId=commandId and no prepaymentId. Thus a supply incurred payable paid later by that command is absent from the supplier movement chain, even though the casebook has the exact pay_obligation/obligationId/cash.referenceId facts. The supplier row also does not publish its associated cash legs. A separate obligation row shows payment cash, but does not explain the supplier timeline “incurred → paid → negative correction → restored asset → settle another supplier invoice” in that original chain. This violates the accepted contract's original-order explanation; it is not a finding that core money is incorrect.

Required minimum: take original obligationIds from this supplier pool's original incur_supplier_usage chain, include exact later pay_obligation records by those IDs, and attach the original station-account cash by operation id plus obligation referenceId. Preserve original operation order; a settle_supplier_credit is credit used to pay an original invoice and has no new cash. Retain cross-period/site ownership and distinguish actual cash from pool paidFen. Do not infer the reversal split from today's total credit. Current tests cover a true paid-supplier negative correction and show the reversal is noncash, but not a subsequent original payment plus later credit settlement/refund read through the supplier row.
